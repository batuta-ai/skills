## Decisions and context

The core contract is the grants section of core `docs/loop.md` at v1.1.0-beta.58. The facts below come from it; do not invent behaviour beyond them.

- Command: `batuta loop --transport <mode> --answer <task> --allow-path '<glob>' --allow-op <ops> --until task "<text>"`. The grant flags go before the answer text, because flag parsing stops at the first positional argument. `--allow-path` and `--allow-op` repeat. `--until task` is the only duration and the default: the grant lasts until the task ends in this delivery and never reaches another task or delivery. Grants only add; the task's standing grant is the union of its grants, at most 32 paths and 16 operations.
- A path glob is clean and repository-relative (`docs/**`, not `docs/` or `./docs`). Absolute paths, `..`, backslashes, invalid globs and boundary paths are refused with exit 1 and an error naming the path. An operation is a lowercase token (`^[a-z][a-z0-9-]{0,31}$`) in a comma list; the runner compares operations by equality, so the answer text names the exact tokens.
- Boundary paths no grant reaches, whatever the glob: `WORK.md`, `.batuta/**`, CI configuration (`.github/**` and the other CI files), licenses and lockfiles at any depth. A boundary file the plan Scope itself names stays allowed. So a question that needs a boundary path is answered by changing the plan Scope (back to `/batuta-plan` and a new approval) or by answering no, never by a grant.
- The runner replies without parking when a granted task asks a question with no `Beyond grant:` clause or one whose items are all granted. It parks as `waiting_input` otherwise; the ask file and the `question_recorded` journal record then carry `grant_park: <reason>` and, for `not_covered`, `beyond_grant: <items>`. Reasons: `not_covered` (the clause names ungranted items), `malformed_clause` (the clause breaks the grammar), `turn_cap` (3 grant turns used in this execution), `repeat` (the same question as an earlier grant turn), `deadline` (no time left for another turn). A park without a grant has no such keys.
- Version check: grant flags need core v1.1.0-beta.58 or later. Detect them with `batuta loop --help` listing `-allow-path`, not by comparing prerelease strings. Without them, answer with text only, as before.
- Trust limit: the executor reports its own coverage, and the scope gate and boundary paths still decide what lands. A grant is an authorization the user gives. The conductor writes one only when the user's answer, or a plan Decision written for that case, authorizes those paths or operations. A loop-first project's `critical` lane has no conversation, so its plan Decisions must carry the grant the session would have given.

- Release: both tasks are in the `general` domain on purpose. The loop derives the commit type from the domain, and `docs` would commit as `docs:`, which never drives a release; `general` commits as `feat:`, so the merge cuts a minor release the host can vendor.
- Checked before approval: only step 5 of `skills/batuta-loop/SKILL.md` teaches the `--answer` command. `skills/batuta/references/dispatch.md`, `skills/batuta/references/routing.md` and `skills/batuta-init/SKILL.md` only name `waiting_input` or `BATUTA-QUESTION`, so they stay as they are and the cycle packet does not change.

**Task 1.** Write `skills/batuta-loop/references/grants.md` as host-neutral prose for the agent that relays a parked question. Sections, in this order: when to grant (a scope question about paths or operations the user authorized; the Tempo case, where an answer without a grant made the next session ask again); how to write it (the command form above, the smallest globs that cover what the question names, one `--allow-op` token per operation the answer text names); what never to grant (boundary paths, `**` or wide globs as a shortcut, paths outside the task's purpose, anything the loop never does such as merge or push); reading a park under a grant (one list line per reason, in the exact form ``- `<reason>` → <action>``, so the gate can anchor on it (plan proofs anchor on ``^- `<reason>` `` only, because the loop splits an Accept entry at its last arrow): `not_covered` → relay the `beyond_grant` items and, if authorized, answer with a grant that adds exactly those items; `malformed_clause` → answer restating the clause form `Beyond grant: paths: <paths>; operations: <operations>`, no new grant; `turn_cap` and `repeat` → read the questions, answer the real decision, and consider whether the task needs splitting in the plan; `deadline` → answer to resume, and name `--task-timeout` if it recurs); the version check. In `skills/batuta-loop/SKILL.md`, extend step 5 within its one paragraph: a scope answer can carry `--allow-path`/`--allow-op` before the text, and cite `references/grants.md`. Keep the SKILL.md body under its 60-line budget and do not touch the other steps.

**Task 2.** In `skills/batuta-status/SKILL.md`, the "parked with a question" state also shows the `grant_park` reason (and `beyond_grant` items) from the ask file when present; keep it to the existing bullet. In `tests/skills/check.sh`, next to the other contract greps, add one-line checks that `skills/batuta-loop/SKILL.md` cites `references/grants.md`, that the reference has the anchored ``- `<reason>` →`` line for each of the five park reasons, and that it names `--until task`. Write `tests/skills/grants_mutation.sh`: for each mutation (the citation removed from the loop skill, each of the five reason lines removed in turn, `--until task` removed) it copies the repository's `skills/` and `tests/` to a fresh temporary directory, applies the mutation there with portable tools (no `sed -i`, which differs between BSD and GNU), runs `bash tests/skills/check.sh` in that copy, and fails when the gate passes. It never edits the checkout, removes its temporary directories, prints one line per mutation, and exits 0 only when every mutation failed the gate. Do not call it from check.sh.
